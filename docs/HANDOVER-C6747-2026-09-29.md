# Handover: the C6747 as a benchmark box, 2026-09-28 to 2026-09-29

Where the tms6747 work stopped, what was measured, and what to do next. Branch
`tms-opt`. The standing tables are in CLAUDE.md ("TI's own C6747 toolchains as
three boxes" onward); this is the state of the round.

## The goal, as the user set it

cpp11 + ASM6x + LNK6x for the C6000 should match TI's own compilers - CCS 7.4's
cl6x 8.2.2 and CCS 5.5's cl6x 7.4.4 - for speed at -O2 and for size at -O1, with
TI's toolchains on three boxes as the oracle and the Mac as the host where the
compiler is improved. Two priorities: (1) the whole toolchain competing with
CCS 7.4 and CCS 5.5 on their boxes; (2) Compiler++ compiled by every toolchain
and its speed compared on TI's simulator, on Windows (CCS 5.5, CCS 7.4) and
Linux (CCS 5.5).

## The boxes

| box | compiler | runs on |
| --- | --- | --- |
| windows-ccs74-vm | CCS 7.4, cl6x 8.2.2 | VM6747 (CCS 7.4 has no simulator) |

| linux-ccs55 | the same, on ec2-user@52.202.164.123 | the same simulator |

**The Linux box has 419 MB and two vCPUs of one core.** Never run two DSS
sessions there at once - two thrashed it and it needed a reboot on 2026-09-28 -
and expect a run to take about 1.3 times as long as on Windows. The Windows PC
has 20 logical processors and 64 GB, and runs many sessions at once; simulated
cycles do not depend on host load, so parallel runs change no count.

**Box time is capped at 30 minutes per run** (the user's instruction,
2026-09-29). A ten-file Compiler++ run does not fit - TI's build took 49 minutes -
so the workload is run one file per simulator run, all at once:
`tools/c6747/compilerpp/run-split.cmd` and `run-one.cmd`, with `harnessFile`
written by `runca.js` after the load has run to `main`, and `runca.js`'s script
timeout set to 1,800,000 ms.

## The Compiler++ benchmark

- `tools/c6747/compilerpp/make-harness.py` amalgamates Compiler++ into one file
  and compiles the workload into it as strings: the simulator has no files and no
  argv. `--workload <dir> --rounds <n>` makes the timed harness - each file
  compiled n times, nothing run, a fingerprint (FNV over functions and
  instructions) printed per file, which every build must agree with clang on.
- `tools/c6747/compilerpp/workload/`: ten files, 1,497 lines, in Compiler++'s
  language (no templates, exceptions, `?:`, `static`, `sizeof`, casts, ...).
- `tools/c6747-compilerpp [rounds]` is the whole-harness driver (Windows and
  Linux, five builds). It predates the 30-minute cap: use run-split for the full
  workload.
- `tools/c6747/prof.js` samples the PC every N ms of wall time;
  `tools/c6747/prof-map.py out prof [top] --map map` maps samples to functions and
  prints the program/library split. Profiling perturbs cycles by about 2%, so a
  count is always taken from an unsampled `runca.js` run.

## The two changes

**`1273e64` include/string: fifteen units inside the object.** Every string owned
a heap buffer, so 52% of cpp11's cycles were rts6740's `free`, which walks its free
list. Malloc 11,983 -> 2,112, free 10,609 -> 3,027, peak live blocks 4,176 -> 1,518
on one file; 2.52x -> 1.32x. A null heap pointer means inline - never a pointer
into the object, because cxx1 hands a returned local to its caller as bytes.

**`ab3d062` Tms6747: small members walked in place at -O2.** The C6000 backend had
no inliner. Callees of at most 12 AST nodes, nested three deep, all arguments in
registers, no struct parameter or result, not noexcept; the callee's locals past
the caller's frame; a function with a landing pad reserves room up front. The
x86 budgets alone grew .text 35% for 5.4%; 12 nodes gives 4.0% for 10%.

## Found and not fixed

- cxx1 refused `c ? p : q` between `char *const` and `const char *` (composite
  pointer type). Another session took it (`task_79034182`); its parser change and
  cases are in the working tree, uncommitted, and it rewrote `p() const` in
  `include/string` back to the `?:` form there. HEAD keeps the `if` form, which
  builds without the parser fix.
- cpp11 accepts `const struct point *p = a;` with `a` a `const void *` (C, and
  ill-formed C++).
- asm6x warns "value truncated to 16 bits" in exception tables for functions past
  64 KB.
- `<vector>`'s `grow` copies elements by assignment and never destroys the old
  ones: a `vector<string>` leaks each heap string when it grows.
